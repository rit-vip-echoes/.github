# **Playtest Preparation Guidelines**

## Creating a new Release

Before each playtest, teams must create and deploy a new build following the [deployment guide](https://github.com/rit-vip-echoes/.github/blob/main/profile/webGLBuild.md). This build should be to the main branch, not the dev branch!

Afterwards, leads must create a new Release in GitHub.

1. In the new release screen, create a new Tag and name it (semester number)-s(sprint number).
    -  Example: 2261-s2
2. In the release title field, name it (season) (year) - Sprint (sprint number).
    -  Example: Fall 2026 - Sprint 2
3. Make sure the target branch for the release is "main", not "dev"!
4. Use the "Generate Release Notes" feature. This creates a list of all changes since the last release, linking the appropriate PR and users in an organized list. It additionally highlights new contributors and links to a full change log since the last release.
5. Above where the release notes are generated, write a Release Overview. This should include a summary (written by you) of the changes since the previous release, including any known bugs.

See [this release](https://github.com/rit-vip-echoes/Dream-Swimmer/releases/tag/Summer2026) as an example.

## Before The Playtest

Before each playtest, aside from building and releasing the newest version, teams need to know what they want to get out of a playtest!

Try to come up with a few things:

- In the release notes, as a team come up with 2-5 experiential goals you want to get feedback on for an upcoming playtest. 
   - These can relate to mechanics, aesthetics, anything in the game but should connect back to an experience the players have. 
   - Try to avoid vague "is new thing good/bad" goals.
 - create a short set of internal interview questions, no more than 5, to ask players after they're done playtesting.
   - these should avoid being too broad or vague and should not be leading questions; you want more from players than a simple "yes/no" answer. 
   - questions should tie back to the experiential goals and help you answer them, while also gaining player insight.
- if there's an element or mechanic that you want the players to test and utilize but do not have onboarding for the mechanic created yet, then please create a small index/note card which gives instruction on using the mechanic or player goals.
  - This should only exist until onboarding is created, it should not serve as a replacement for player onboarding! 
  - This also can include player controls if your game does not have instruction yet on player controls.

This instructional index card can also include hints if there are known vague/unexplained parts of a game, but these should be kept to a minimum. Also include content warnings here. 

## During The Playtest

Things your team needs to bring to bring to a playtest:
    - your game (using the web deployed build, not the Unity editor) is set up across 3-5 machines
    - if your game includes audio, provide working headphones. 

When someone comes to playtest a game, please encourage them to state their thought process out loud. While you are observing someone playtesting, however, DO NOT SAY ANYTHING. Players' experiences of the game should be minimally influenced by the developer watching over their shoulder. 

During the game, the team watching over playtesters should have a shared document with their team in which they record:

- the player's name 
- how long they played the game for
- any observational notes
- anything the player says
- player's words via audio (if the player consents to it and the room isn't too loud)
- screen record players' gameplay (again, if they consent to it)

Afterwards, interview the players on their experience, using the internal interview questions created before the playtest. Feel free to come up with follow up questions and adjust to the flow of conversation, just keep an eye on time and if anyone else is lined up to playtest the game.
